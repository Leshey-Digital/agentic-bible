# Hosted contribution and review preparation

This code prepares the existing twenty-article inbox for trusted hosted composition. The shipped entrypoint still supplies no contribution adapter and accepts no public suggestions. Existing D1/trust/token bindings, local cookies, caller roles, email address records and lookalike flags cannot activate intake or sign-in. No account, real key, provider connection, deployment or policy approval is created.

A trusted server composition can pass `Ports.contributions` with valid existing signed RS256 trust, a privacy-preserving ingress client-key function, and a policy naming future approved contribution terms and privacy paths, revision and moderation readiness. This adapter is server code, never client JSON or an env enable flag. No contributor license or consent is invented. The current verifier still pins the existing staging origin; production origin/identity setup is a separate dependency. Policy paths are same-origin bounded paths; the owner must actually supply approved documents before live mounting. The adapter must derive its `hosted:<sha256>` rate key from authenticated ingress metadata, never an arbitrary browser header. Hosting must enforce ingress/concurrency bounds and exclude request bodies/assertions/private records from logs and traces.

`/api/editorial/status` reports explicit unavailable reasons and exposes only configured policy paths/revision. The contribution form stays disabled unless its matching local synthetic mode or an explicitly policy-configured hosted mode is returned. Hosted copy names editorial review and does not claim email delivery. The shipped form remains on hold.

## Routes and authority

- `POST /api/submissions` accepts exactly the existing six contribution fields, the compiled twenty-entry inventory, validated plain text and HTTPS source links. Sources are retained, never fetched. Same-origin and fetch-metadata checks apply. Streamed actual bytes are limited to 8 KiB and reading to one second.
- `GET /api/admin/submissions` and `GET /api/admin/submissions/<id>` directly invoke the existing cryptographic verifier. `X-Agentic-Bible-Request: admin` is required; local sessions and the legacy optional verifier callback are insufficient. Reads return bounded pages/audit.
- `PATCH /api/admin/submissions/<id>` requires same-origin signed authority, exact disposition/tags/version fields and a current optimistic revision. Hosted updates have finite per-item/global audit capacity. Changes do not publish.
- `POST /api/admin/submissions/<id>/review` requires an explicit reviewed note, current submission revision, source commit/Markdown hash and existing allowlisted citation. Any article in the compiled twenty-entry inventory in `follow-up` can enter its own canonical proposal path. The target is derived from the stored submission, never a client-selected path. New approvals use schema 2 with explicit article ID and derived canonical content path; legacy schema 1 remains unchanged.
- `GET /admin/contributions/` and its CSS/JS assets require the same real signed trust. The private interface provides filters, suggestion details, editable dispositions/tags, audit and explicit reviewed-note forms. Errors retain drafts; confirmed tag updates do not depend on a follow-up read. The existing `/admin/corrections/` remains the proposal/revocation interface, with standalone creation hidden only when actual-inbox composition is mounted. Source previews load the stored item’s pinned article/citations before enabling review; saved proposals display their article target.

The submitted review is admitted in one actual D1 batch: immutable existing `hosted_reviewed_notes`, new `hosted_submission_reviews` binding and editorial audit. Every follow-up insertion correlates the complete winning candidate, including owner/input/note/fingerprint/server timestamp and current eligible submission revision. Conflicting approval IDs cannot create authority or audit. Identical successful review replay returns existing authority without another audit.

When actual contributions are mounted, the legacy standalone create route rejects new notes with `actual_submission_review_required`; existing active old-format notes remain readable/replayable. Without that adapter, the existing standalone signed review path remains available.

Legacy reviewed notes preserve their input schema containing `submissionId`; the new review command omits that field and binds its URL item through the immutable new table. Lookup requires this binding for the new command format. This avoids querying a nonexistent new table for legacy stores while failing closed if new-format binding is missing. Changed revisions, rejected/dismissed submissions or revocation invalidate bound proposal authority, including completed-proposal replay. Existing repeated proposal rechecks, request budgets, controlled GitHub transport/outbox and draft-only receipts remain authoritative. Git stays canonical; no direct publish/revert is added by editorial dispositions.

## Persistence, limits and verification

Migration `0018_hosted_submission_reviews.sql` is additive and preserves existing submissions, history and legacy notes. Existing 0017 is retained for twenty-entry intake. Rate windows have a finite 2,048-row admission cap; each client has five distinct accepted suggestions per ten minutes, duplicate replay remains idempotent, and the inbox retains its 1,000-row cap without eviction. Hosted updates stop at 64 item audit entries / 16,000 global entries. New schema-2 actual-inbox notes and their proposal outbox have a finite 64-row total lifetime capacity, sufficient for the twenty-entry collection and bounded follow-up. Mounted inbox lists at most 64 notes. Legacy schema-1 standalone creation/default outbox and ordinary lists retain their four-row capacity; no per-invocation/lifetime HTTP/request/retry or paid-work budget increases. Capacity closure requires deliberate owner-reviewed archival/recovery; no automatic deletion/reset is supplied.

Run `node --test tests/production-hosted/*.test.mjs`. Native proof uses actual workerd/D1, generated disposable assertions, explicit synthetic policy and a controlled GitHub transport. Coverage includes all twenty IDs, shipped/policy closure, signed claims/local-forgery/CSRF checks, replay/restart, bounded input, rate/capacity, tag/version/audit, actual reviewed-submission draft proposal, stale authority and injected D1 rollback. All twenty articles also complete source-specific signed review/proposal/restart checks. One persistent D1 store completes twenty distinct article drafts without resetting data or budgets between articles, using twenty explicit synthetic ingress clients and supplied pinned controlled Git source. It reaches 64 review/binding rows, injects an actual D1 audit fault at the capacity boundary, proves atomic rollback/restart and checks bounded listing/outbox closure before network dispatch. Its remaining outbox capacity rows are explicit synthetic fixtures, not a claim of 64 real GitHub draft calls. Fixture tests establish code behavior, not live gateway membership, policy approval, provider permissions, email delivery or release readiness.

Rollback removes the trusted composition/routes/UI and preserves additive data. Once bound notes exist, retain a compatible lookup implementation: older readers do not enforce the new actual-submission binding. Do not silently downgrade authority or delete history.

## Reservation-response authority correction

Each controlled GitHub mutation now rechecks durable approval, revocation and any bound submission after its request-budget reservation await, then checks assertion expiry and invocation deadline synchronously immediately before invoking the transport. A reservation response delayed across dismissal, a new item revision, revocation or expiry cannot dispatch its corresponding mutation. The consumed reservation remains charged across failure/restart; no automatic retry or refund occurs. Existing final authority checks and recovery receipts remain in place.

This closes the reproduced delayed-reservation window. A D1 snapshot does not atomically serialize a remote provider operation with a concurrent later revocation. Work already started while eligible may complete after an administrative change; transport ambiguity remains conservatively retained. No distributed atomicity or retroactive cancellation is claimed. Tests hold actual committed D1 reservation responses before trees, commits, refs and PR writes, invalidate authority, then verify zero corresponding mutation dispatches and retained counts/restart closure.

## Versioned article targets and legacy compatibility

Schema-2 approved notes and proposal receipts record `articleId` and `contentPath`, derived only from the existing compiled reading inventory. Canonical paths remain `src/content/articles/<articleId>.md` in the one existing repository. Authority fingerprints/replay receipts include the target. Bound lookup compares the actual stored submission article and version to the immutable note. A submitted source hash from another article fails before a mutation. Fixed credential transport permits only the twenty compiled article content paths; no arbitrary path, repository or endpoint is accepted.

Pinned source previews require a regular non-symlink Git blob from the exact verified main commit/tree. Schema-2 projection validates the bounded source-declaration subset from that exact Markdown and only permits its source IDs; absent citations fail before any remote write. New notes append an escaped plain-text correction and source anchor, preserving every unrelated tree entry. Review source hashes are rechecked at proposal time; an approval is not proof the admin’s supplied source pins were current. Source-preview request budgets and existing final main/source checks remain conservative.

Legacy schema-1 standalone notes/receipts retain exact target/title/validation and retry semantics. Existing schema-1 actual-submission bindings from the initial checkpoint also remain readable/replayable without rewriting records. New schema-2 fields do not migrate or reinterpret earlier authority. Older implementations reject schema 2; once such records exist, use a compatible reader and do not downgrade to an older authority implementation. Production-origin trust stays an explicit launch dependency: this checkpoint retains exact staging origin/RS256 audience/subject pins, without configuring live identity.
