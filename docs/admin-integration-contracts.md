# Admin integration settings contract

The original reviewed checkpoint `b974c4c20621d7d869fc7a6cf15f4dc8bf89344a` supplied an **unmounted server contract**, not a working hosted secret vault. `src/integration-settings/contracts.ts` exports types and a callable request handler. The [hosted boundary successor](hosted-integration-settings-boundary.md) now imports that unchanged contract into one exact API route with optional trusted server-code adapters; shipped configuration still provides none and remains 503 unconfigured. No persistent binding, database migration, UI, credential, provider call or deployment is added. Storage implementations remain disposable memory in controlled tests. Existing [measurement settings](measurement-settings-contracts.md) keep their non-secret identifiers and behavior.

The single integration identifier is `github-content`, matching the existing documented content-proposal purpose. Extending the identifier union requires a reviewed contract and fixed scoped adapter; clients cannot supply a URL, provider, account, endpoint, headers, role or owner. This contract neither reads nor changes `GITHUB_CONTENT_TOKEN` or existing hosted configuration.

## Identity and input

`createIntegrationSettingsContract` accepts server-only trust configuration and trusted storage/test adapters. It validates trust with the existing `adminTrust` parser and verifies each request cryptographically with `verifySignedAdmin`; it does not accept a verifier callback or caller identity object. Existing pinned RS256 issuer/audience/subject/key/expiry checks apply. The exact hosted staging origin, `X-Agentic-Bible-Request: admin`, and absence of cross-site fetch metadata are mandatory. POST also requires the exact Origin header. No CORS permission or production identity setup is added. Expiry is checked again before secret replacement/test dispatch and private reads.

GET returns status for the sole integration. POST accepts JSON with exactly `integration`, `operation`, `revision`, `requestKey`, plus `secret` only for `configure`/`rotate`. Operations are distinct: initial configuration requires revision zero and no existing record; rotation requires an existing owned record and its current revision. Request references are lowercase UUIDs. Unknown fields, wrong types and unsupported operations/targets fail without echoing input.

The streamed reader enforces 8 KiB of actual UTF-8 body bytes and a one-second body deadline, independently of Content-Length. Secret input is 16–512 UTF-8 bytes (within the existing hosted credential transport limit), without whitespace/control characters. This is a conservative input bound, not GitHub ownership, validity, permission or token-format verification. A secret is handed only to the trusted transaction's write-only replacement function. There is no secret read function in the handler interface. Hosting must additionally bound ingress/concurrency and exclude request bodies and adapter exceptions from access logs, traces and error reporting; those infrastructure controls are not configured here.

## Atomic ownership, rotation and audit

The storage adapter must serialize operations per integration and atomically commit or roll back secret replacement, metadata and audit together. The first successful signed admin owns the record. Other signed admins cannot read, rotate or test it. A future transfer/recovery policy needs separate review. Concurrent rotations with the same revision have one winner; stale revisions cannot overwrite current state.

Every accepted command consumes its request reference permanently within the bounded record. Replaying **even identical input returns 409** and never performs another replacement/test. Reload current status and use a new reference after reviewing the outcome. No secret-derived fingerprint is retained for retry equality. There is no exact-response replay or durable persistence claim. At most 64 accepted command references and 64 audit events are retained, without eviction; capacity failure has no mutation effects. Test reservation and completion each consume an audit slot. No archive/reset/delete path is supplied.

Audit events contain only operation, revision, a server-generated event UUID, server timestamp and an allowlisted outcome. Submitted request references, secret bytes, suffixes, hashes, assertions, raw subjects and provider text are excluded from audit projections. Private metadata contains the existing opaque signed-admin reference and bounded client request references for ownership/replay; it is never returned wholesale. Rejected authentication/validation requests do not create audit rows in this contract. Errors are fixed codes with no exception text.

Rotation means atomic **replacement in the future storage adapter**. It does not issue, revoke, rotate or validate a token at GitHub, change account permissions, or alter existing credential bindings. No encrypted persistent storage, encryption keys, retention/export/recovery plan or provider rotation adapter is implemented. A production adapter must prove transactional secret handling and crash/restart behavior with its actual storage system before mounting this handler.

## Status and bounded connection tests

Responses contain only `integration`, `configured`, constant `maskedSecret` (`********` or null), revision, connection enum and redacted audit. Mask length/suffix/status never derives from credential bytes. `configured` means a record exists; it remains true when a test fails and does not establish live readiness. All responses are no-store/noindex with MIME sniffing disabled. Nothing writes static assets or public policy output.

A test command first reserves its reference, revision, lifetime test count and audit space atomically. At most eight tests per integration record are admitted across rotations; rotation does not reset the budget. The trusted test adapter receives the fixed integration, exact revision and abort signal, never a client-selected destination or submitted secret. It must resolve only that credential revision through secure storage, refuse changed revisions, use a fixed minimally scoped read-only endpoint, cap response bytes/requests and honor abort. No such live adapter is supplied.

The handler waits at most one second for the adapter result, aborts, and returns only `connected`, `rejected`, `unavailable` or `timeout`. Only exact `connected`/`rejected` adapter strings are accepted; objects, unknown strings and all exceptions become `unavailable`. Raw provider responses and errors are never forwarded or audited. The handler's deadline cannot terminate synchronous work or force an adapter that ignores abort to cease external activity; transport enforcement remains a trusted-adapter requirement.

Immediately after the reservation await, the handler checks assertion freshness and calls the adapter in the same synchronous callback, before its first await. No queued promise hop separates that check from invocation. If the assertion has expired, dispatch is denied while its pending reservation, audit and budget remain retained. Adapter invocation that starts before expiry is permitted; expiry before completion denies the response without replaying work. Both synchronous throws and asynchronous adapter errors remain redacted.

Rotation invalidates a prior pending completion. Its late result returns stale revision and cannot overwrite the new credential's `never` status. Interrupted or failed completion stays pending, with the reservation and budget retained; replay never redispatches. No automatic retry, refund or reconciliation is implemented. Rotation can supersede a pending test with a new revision. Software request counts are not monetary caps or GitHub rate-limit proof.

The core reservation/completion checks do not prevent every stale external operation. If storage delays its reservation response while a rotation commits, the handler can still call the adapter with the older requested revision. The trusted adapter must serialize its revision validation with credential resolution and the start of its operation, refuse a changed revision, and avoid using retained old credentials. No production adapter or claim that the core alone prevents such dispatch is supplied.

## Verification and rollback

Run `npm run test:integration-settings`; it is included in `npm run validate`. Generated disposable RS256 assertions exercise the actual verifier. The disposable atomic fake proves handler contracts for ownership, competing writes, rollback, replay, masks, body bounds, quotas, interrupted pending tests, stale completion and redaction. These original contract tests do **not** prove a persistent vault, actual Worker routing, real network/transport bounds, live gateway membership, provider permissions or hosted readiness. The separate successor's `test:hosted-integration-settings` adds actual local Worker routing proof with test-only memory adapters and shipped default closure. Existing settings tests verify retained non-secret behavior. No UI/browser path is added.

Original-checkpoint rollback removes the module, focused tests, npm command and change documentation. On the hosted successor, first revert its route/type seam as documented there before removing the contract import. No resource or stored production data exists to migrate. Wiring persistent secret/provider adapters still requires a separately scoped implementation, independent review and specific setup authority.
