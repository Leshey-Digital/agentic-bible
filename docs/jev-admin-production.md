## Provider contract and capability boundary

Official references checked on 2026-10-19:

- [Typesafe launch article](https://typesafe.ai/blog/introducing-system-one-models-and-jev).
- [HTTP API](https://docs.typesafe.ai/api): fixed POST evaluation endpoint, bearer authentication, state/questions request, typed answers and token usage.
- [Models](https://docs.typesafe.ai/models): explicit version IDs, input-token pricing and free output tokens. No rate is silently imported into budget policy.
- [Jev with coding agents](https://docs.typesafe.ai/introduction/coding-agents): no prose generation.

`src/maintenance-adapters/jev.ts` implements a real protocol transport with injected dependencies; it does not send live requests by default. Its one fixed Noul question provides advisory editorial attention signals, never factual or publication authority. Model IDs are pinned explicitly. Configuration must supply an enabled flag, credential, allowed model, transport and charged-execution authority; missing/invalid dependencies stop before dispatch. Requests and streamed responses have byte/deadline/cancellation limits. Redirects, unknown response fields, invalid usage/model/probability and provider errors fail closed with redacted codes. One invocation admits at most one transport dispatch; no automatic retries occur.

Jev cannot implement the requested article prose generation. The exact missing contract is a prose-capable generation provider/model and its endpoint/authentication/request/response/usage semantics, or a separately approved supplied-content workflow. `generate()` rejects without invoking Jev. A protected `POST /api/admin/jev/evaluate` route requires the trusted signed-admin port, same-origin/CSRF checks, and accepts only bounded `content`. It cannot select a model, question, endpoint, credential or budget. It returns advisory structured-decision output only. `configuredPorts()` now mounts `createJevDispatchPort` only when the vault and explicit `JEV_DISPATCH_POLICY` parse successfully; the binding must contain `enabled`, a supported pinned `model`, `inputTokensPerByte: 1`, `outputTokenUpperBound: 2048`, and an owner-supplied `currency` policy with matching Typesafe provider/model/tokenizer pricing and actual currency limits. Missing policy remains `not-mounted`; complete configuration with `enabled:false` remains `disabled`. No caps or live policy are selected here. The vault's resolver decrypts under the durable lock and releases a credential only when its owner reference matches the route's verified signed-admin subject. The shipped Worker has no such binding configured in this preparation; no live call, schedule, article producer or writer is connected.

`src/maintenance-adapters/jev-currency.ts` now implements a trusted D1-backed charged-execution authority over the existing proposal currency ledger. It requires injected Jev-specific upper-bound functions for input and output token usage, validates the exact provider/model/tokenizer price identity, reserves before dispatch, revalidates durable currency authority immediately before the request, settles the provider's documented usage values and holds the maximum reservation after uncertain outcomes. The configured entrypoint uses the conservative input request-byte bound and the fixed 2,048-byte response ceiling as token upper bounds. The authority remains unavailable until the owner supplies an explicit runtime currency policy and enables the configured model; no actual cap is supplied by this change.

`src/maintenance-adapters/cloudflare-prose.ts` is a separate injected Workers AI prose-draft adapter using the official `AI.run(model, { prompt, max_tokens })` binding contract. `readCloudflareProseUsage()` parses the pinned model's generated Workers AI output type (`workerd` 1.20261012.1): `usage.prompt_tokens`, `usage.completion_tokens` and `usage.total_tokens`. It requires safe integer counts, checks that the total equals input plus output, and rejects missing fields, aliases and unknown fields. The official model page describes the `usage` object; the pinned binding type supplies the nested fields. The adapter still requires a trusted input-token upper-bound function, returns an unverified draft and cannot publish. It is disabled and no `AI` binding is added to Wrangler or a hosted route.

The existing ledger cap is local application accounting. Cloudflare AI's daily Neuron allowance is account-wide and cannot be guaranteed by this application's ledger when other workloads share the account. Owner approval, account-level spend review and alert/stop setup remain necessary. Controlled fixture success is not provider connectivity, billing verification or production readiness.

The shared D1 currency ledger now supports immutable versioned monthly policies with bounded provider/model/tokenizer price cards. Rotation appends one successor to retained history and atomically advances the active pointer; old reservations keep their original policy and card through settlement. Forked, overlapping, stale or uncertain history fails closed. This removes the code-level 32-day policy-expiry blocker, but does not supply owner-approved prices, spend allocations, Jev token bounds, a rotation operator or live credentials. The Cloudflare adapter's deadline races the binding call but cannot cancel an `AI.run()` already in progress; timeout leaves the maximum reservation uncertain and blocks replay, while the original call may still finish or incur cost. Owner account controls are still required.

The UI source is present on this feature branch. The last recorded live staging check, dated 2026-10-18, identified `b41a422881921638833f92b2361a70eb1647d01f`; a later staging refresh could not be verified from this environment. Jev checks remain unavailable: the documented evaluation endpoint is billable and no documented non-billable credential check has been established. Direct test commands fail before reserving or dispatching.

Migration `0023_jev_integration_vault.sql` atomically rebuilds the two fixed-ID tables. It preserves existing GitHub ciphertext/AAD and retained crash locks; Jev has independent ownership, revision, replay, audit and locks. Ciphertext is authenticated against its integration ID, preventing cross-provider substitution. Production migration execution is not performed.

The UI preserves editorial review and GitHub draft workflows, distinguishes a review from a source change/release, shows artifact-manifest status without claiming live production serving, disables writes when state/ownership/access is unknown, clears secret input after attempts and selection changes, and requires explicit replacement confirmation. A lost mutation response requires reloading the masked revision before retrying. Secrets are never returned or put into generated assets, audit or client storage.
