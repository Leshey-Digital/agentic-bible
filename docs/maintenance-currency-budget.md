# Controlled USD maintenance budget

This separate local successor preserves frozen PR44 `d0a4f9b4648bb66fe7acac7ba69b95a7e98b36f4`. The [controlled pipeline](controlled-maintenance-pipeline.md) already joins source capture, provider generation, canonical Git and signed review. Its existing proposal ledger used simulated units. This component adds exact USD accounting on those same D1 proposal rows, without a second job/charge ledger, provider credential, paid call, remote migration or deployment. Independent review and publication are separate steps.

## Explicit activation and price basis

The existing pipeline and fake provider remain default-disabled. Trusted code may additionally supply `currency: {enabled: true, policy}` to `runMaintenancePipeline` or `runMaintenance`. Omission retains the existing synthetic demonstration mode on an unconfigured store. An explicit disabled/malformed currency control stops. Once currency policy is pinned in a store, a caller cannot omit it to admit new simulated jobs. Existing completed synthetic receipts remain readable; enabling currency over any pre-existing unpriced proposal is rejected rather than assigning invented prices or clearing charges.

A policy names schema/version, USD unit, shared account scope, run/day/month limits, day/month baseline allocations and one explicit price card. Integers are **micro-USD**: 1,000,000 equals $1. Pricing identifies card, provider, model, tokenizer and the `input-output-tokens` basis, separate micro-USD rates per million input/output tokens, a per-request fee, and finite valid-from/until times. Each dimension rounds upward independently with BigInt arithmetic. Missing/zero rates, unsupported dimensions, unsafe numbers, expired pricing and provider/model/tokenizer mismatches stop before a model invocation. There is no fetched/default live rate or automatic price inference.

Only the existing deterministic extractive fake and its `synthetic-utf8-bytes` tokenizer can execute through this pipeline. Its trusted byte counter and strict response schema supply the measured usage; this is **not** a tokenizer or billing claim about any commercial model. Controlled rate cards price those test units in actual USD denominations to exercise enforcement without spend. A real adapter must first prove an upper bound for every billed dimension, including any request, reasoning, cached, tool or other fees. Unknown dimensions are unsupported, not free.

## Reservation, settlement and periods

Migration `0016_maintenance_currency.sql` adds policy, reserved/actual micro-USD, usage, settlement time and currency state to `maintenance_proposals`. The one-row `maintenance_currency_policy` table stores configuration and clock high-water only; all event reservations and charges remain the existing proposal records.

One D1 batch pins the policy, advances its monotonic clock and inserts an owned proposal only when the existing request/count/simulated limits and the USD guards all pass. USD reservation is known input at the explicit price plus maximum output plus request fee. It must fit the run limit, the current UTC day plus its baseline and the UTC calendar month plus its baseline. Existing capacity remains sixteen retained jobs, with one unresolved operation at a time. No balance can be bought, topped up or increased by a retry.

After the reservation response and a fresh durable reservation/policy-authority read, the producer checks the clock synchronously after the last await and canonical-base check, immediately before provider invocation. The pinned price must still be valid, time must be at least the reservation and durable high-water time, and its UTC day/month must match the reservation. Expiry, midnight or backward time before dispatch produces zero provider calls. The full reservation stays held conservatively; restart/replay does not infer a refund or permission to dispatch. The [dispatch correction](../openspec/changes/maintenance-dispatch-eligibility/proposal.md) records the original reproduced P2 and regressions.

Validated response usage settles the same owned row atomically with its response and publication packet. Admission counts actual settled micro-USD and full unconfirmed reservations. Only known unused output reservation becomes available for another admitted job; no uncertain reservation is refunded. Baseline amounts are included once per period in the admission equation, not copied into each job or charged as provider usage. Currency policy and usage are bound into producer/pipeline fingerprints; downstream canonical authorization verifies the settled private row. Public content/history do not expose private budget data.

The policy is immutable for this local store. Increasing a cap, changing the account/card or removing currency cannot bypass it. No policy-rotation, top-up, abandon/refund or archive API is implemented. This intentionally stops at expiry or sixteen retained rows pending a separately reviewed operator procedure. Do not delete/recreate the store to evade held charges. New calendar periods use their configured baseline again; unsettled operations continue to block across day/month rollover. Usage arriving after the admission UTC day, after price expiry or after a backward clock is not accepted as a known settlement.

## Failure and retry behavior

- Concurrent callers compete for the existing unique event/owner and single outstanding job. Losers do not dispatch. Replay binds the same input, policy and price; it cannot reserve or charge the event again.
- A lost reservation reply stops without invoking the provider. If the insert landed, its full reservation remains held; an automatic retry cannot assume the call was never sent.
- A lost settlement reply is reconciled from the durable exact owner/input/response/usage row. If settlement is confirmed, publication can resume after D1 restart without another provider call. Missing readback remains held and stops.
- A timeout, transport exception, rejection, malformed response or unknown/mismatched usage after dispatch is uncertain in currency mode. An HTTP error does not prove no bill. The full reservation remains held and blocks new generation, including a new event or later period.
- Known settlement above the reserved usage, invalid time or changed usage cannot release funds or authorize publication. Historical completed replay verifies the stored settlement and receipt without invoking a provider or reactivating an old catalog.

## Configurable operating target and limits

The requested **$10 monthly target including a $5 Workers baseline** can be represented as `monthLimit: 10000000` and `monthBaseline: 5000000`, leaving at most $5 for this ledger's covered provider calls. A daily baseline allocation and run/day caps must also be supplied explicitly. These are configurable operating-policy values, not a live approved provider allocation, a pricing quote or a deployment decision. Test run/day caps and rates are controlled fixtures only.

This component gates only invocations routed through this trusted function and one shared D1 ledger with a correct clock and price/usage contract. It does **not** cap Cloudflare billing, enforce a vendor-account balance, measure actual Workers/D1/storage/egress/CI/analytics costs, account for unrelated callers or coordinate independent D1 databases. The configured baseline is a budget allowance, not a measurement or guarantee of actual infrastructure charges. Occasional infrastructure overages remain outside this code's authority; unexpected unmodeled costs cannot safely be inferred as remaining model budget. Invoice reconciliation, live price verification, secure provider setup, real execution/transports, alerts and deliberate uncertainty/policy-rotation/retention procedures remain future work. Paid activation stays disabled.

## Reproduce and rollback

`npm run test:maintenance-currency` uses controlled provider responses and actual local workerd/D1 for concurrent ownership, USD/baseline boundaries, UTC periods, pinned prices/policy, settlement/restart/replay, lost reservation/settlement replies and uncertain charges. Its integrated case uses actual owned Git and the signed review Worker after settled generation. `npm run validate` includes it; retained browser/Worker suites, both dry runs and release preparation verify compatibility. Fixtures use owned Git-directory stores and never touch interactive editorial data.

Rollback stops the local runner and preserves all receipts, held reservations and policy. Unmigrated synthetic-only stores remain supported. After USD rows exist, older code does not understand the new guards: a direct downgrade is unsupported. Keep the new guarded reader/enforcement or stop execution; never erase accounting or drop the additive schema to make old code run. No production resource exists to roll back here.
