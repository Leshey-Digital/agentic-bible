The approved architecture is GitHub source/history → validated build → Workers Static Assets. D1 is suitable for bounded workflow metadata, not an alternative canonical content store. An accepted GitHub source change and a new authorized build/deployment must precede a hosted article change. [Cloudflare binding model](https://developers.cloudflare.com/workers/static-assets/binding/) supports serving the asset bundle from Worker code; it does not turn the local filesystem publisher into a hosted write service.

This candidate adds a concrete bounded boundary: a Workers-native, D1-reserved adapter can propose one trusted approved tool-use note as a pinned GitHub commit/create-only branch/draft PR. A separate staging entrypoint serves assets and reports capabilities. Default write ports are absent, so no fixture, flag or client header enables hosted writes. Controlled tests prove the protocol and a proposed Markdown revision builds/searches through the actual local Workers Static Assets runtime; they do not prove live GitHub publication or hosting. [Adapter contract](github-content-proposals.md).

Before hosted corrections can change canonical reading: integrate reviewed source into the chosen release branch; implement approved production identity and immutable approval production; authorize a real D1 binding/migration and narrowly scoped GitHub transport; ensure proposal-created PRs run required CI under the selected credential/event model; enforce review/release head pins and a deployment/rollback path; correct release history references; resolve contribution/legal/privacy/retention gates. No provider/identity or credential choice is made here. No R2/KV/dynamic D1 article overlay, new service commitment or automatic merge/deployment is substituted. Account resources were not re-inspected by this code task; none is created or configured by it.

The [hosted corrections integration successor](hosted-corrections-integration.md) composes PR30/PR31 and supplies the shipped verifier, append-only approved-note producer, credential transport and authenticated admin UI. It closes those implementation-port gaps while leaving live gateway/D1/secret provisioning and canonical release integration explicitly unconfigured. Its controlled signed-identity proofs are distinct from PR30's test function ports and from live hosting.
