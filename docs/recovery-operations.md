# Offsite recovery adapter

The Cloudflare-compatible recovery adapter in `src/recovery/cloudflare.ts` stores caller-supplied recovery bundles in an R2-compatible object bucket and encrypts each object with AES-256-GCM before upload. It authenticates the bucket key, source commit and capture timestamp as associated data, and verifies the plaintext SHA-256 after decryption. The restore path returns the authenticated payload for the existing inventory-verifying restore function in `src/recovery/backup.ts`.

The provisional operating default is one UTC daily snapshot with a seven-day retention window. The default is a code/documentation proposal only; the owner must approve retention, data scope, encryption-key custody/rotation, budget and recovery objectives. The adapter does not register a cron trigger, provision an R2 bucket or D1 database, create secrets, or enable itself. `RECOVERY_BACKUP_ENABLED` must be explicitly `true`, and both `RECOVERY_BACKUP_BUCKET` and `RECOVERY_BACKUP_ENCRYPTION_KEY` must be present before it reports enabled. An optional `RECOVERY_BACKUP_RETENTION_DAYS` may set an integer from 1 to 30; absent it reports seven days.

This adapter does not export Cloudflare D1. It expects a caller to provide a complete serialized recovery bundle. No live bucket, key, scheduled job, upload, or remote restore has been configured or verified. The tests use an in-memory object store and a local recovery tree; they verify encryption, authentication, integrity, retention pruning and restoration only in that controlled environment. A production recovery claim requires an owner-approved data inventory, D1-consistent export strategy, separate key custody, configured bucket and secret, scheduled capture, retained object evidence, and a tested restore into an isolated destination.
