# Optional encrypted integration adapter

`createEncryptedIntegrationAdapters` adds an optional server-only persistence and fixed connection-check adapter for the existing signed write-only contract. The shipped runtime still constructs none. No D1 binding, encryption key, credential, provider permission, production identity or deployment is provisioned. Tests generate disposable values only. This is tested preparation, not a live-ready vault claim.

The owner must supply an actual D1 database with additive migration `0019_integration_vault.sql`, a non-exportable AES-256-GCM `CryptoKey`, a fixed bounded key identifier, existing pinned signed-admin trust and trusted outbound send function. The adapter accepts no browser-selected destination, headers, key identifier or role. Keys are never stored in D1 or returned. Real key provisioning, key rotation/recovery, backup/retention policy and transport/hosting log exclusions remain owner setup and independent review dependencies.

## Atomic encrypted persistence

A single fixed `github-content` row stores ciphertext, a fresh 96-bit nonce, key identifier and the original bounded private metadata. AES-GCM authenticates the complete metadata JSON, integration identifier, format domain and key identifier as associated data. Changing revision, ownership, audit/budgets or ciphertext prevents decryption and closes the adapter. No secret hash, suffix or fingerprint is retained. JavaScript cannot guarantee immediate string-memory erasure; temporary byte buffers are cleared, and no callback/exception/argument is logged.

Storage stages callback changes in memory. Callback failure discards them. One D1 row statement commits encrypted credential replacement, revision, private replay/budget metadata and audit together; a failed statement leaves the previous row intact. Same-revision metadata changes reencrypt the current credential with authenticated new metadata and a new nonce. Rotation requires replacement at exactly the next revision. The existing handler retains its permanent command references, 64-event capacity and eight-test lifetime budget across rotation and restart; it still rejects replay rather than redispatching an uncertain command.

A durable D1 single-integration lock serializes all adapter instances, reads, mutations and connection dispatch. Concurrent admission fails closed without retry. There is no lease timeout or takeover: an interrupted Worker may retain its lock, including after a confirmed commit but before release. Restart then returns unavailable, preserving data and uncertainty. Recovery requires separately reviewed server-owner action; there is no unlock/delete/reset browser endpoint. This conservative availability limitation must be addressed in a reviewed recovery/runbook plan before live mounting. Dropping the lock without checking prior work is unsafe.

## Scoped connection checks

The adapter resolves/decrypts the current credential, checks the exact requested current revision and pending reservation, checks abort, then invokes the supplied transport synchronously while retaining the same durable lock. Rotation cannot overtake credential resolution or operation start, including after a delayed reservation response. A stale revision never dispatches. The fixed request is one `GET https://api.github.com/repos/Leshey-Digital/agentic-bible`, with only the stored bearer credential and fixed protocol headers; redirect mode is manual, browser credentials omitted and referrer disabled. It never follows a client URL, writes content or retries.

The adapter caps actual response bytes at 8 KiB, rejects redirects/unexpected statuses, caps its whole transport/read phase at 900 ms and aborts at the deadline or outer signal. Only `connected`, `rejected` or `unavailable` reach the original handler; raw bodies/provider errors are discarded. The original one-second handler deadline remains independent. The trusted supplied transport must honor abort and prevent request-body/header logging: JavaScript cannot force an arbitrary injected function to stop external activity. Tests use native workerd fetch with controlled outbound responses, never the internet. A successful public repository metadata read establishes only that this fixed read succeeded; it does not prove token ownership, write permissions, live production readiness or a monetary cap.

## Private write-only interface

`/admin/integrations/` and its CSS/JS require trusted integration adapters, direct cryptographic signed trust and the existing exact staging origin. Default configuration returns 503. The interface shows only the contract's constant mask, revision, connection enum and redacted audit. The password field clears immediately when an attempt begins; credentials are never stored in browser storage or put in status/static assets. It never automatically retries a write/check. Unconfirmed outcomes require reloading masked status before a new decision. Rotation replaces server storage only; it does not issue/revoke/rotate credentials at GitHub.

## Verification and remaining gaps

Run `node --test tests/integration-vault/*.test.mjs`. Actual disposable workerd/D1 tests cover authenticated encryption/tamper, owner isolation, masked status, replay/stale revision, rotation/restart, injected D1 commit faults, retained interrupted locks, fixed transport/body/status bounds, lifetime check budget and concurrent rotation versus operation start. Interrupted runtime disposal may terminate dispatch with HTTP500 rather than a network exception; tests accept only those uncertain failure outcomes and verify durable storage afterward.

Existing `test:integration-settings` and `test:hosted-integration-settings` remain separate contract/default-boundary proof. No live identity, real persistent key, provider token, account security change, paid call, remote migration, release or deployment is exercised. A live operator must resolve actual key lifecycle, durable lock recovery, owner transfer, archive/retention, ingress/concurrency and logs before mounting. The earlier unconfigured default and public policy/analytics/advertising defaults remain closed.

Rollback removes the optional trusted composition/UI, preserves encrypted D1 rows/keys under owner control and retains a compatible reader. Never delete ciphertext/history or fabricate a successful connection to simplify rollback.
