## Source history and artifact

`src/release/source.ts` resolves a full Git commit and verifies all twenty current article files against regular Git blobs at that commit. Public file-history links use that exact SHA, never a moving feature branch. `release-source.json` records the source commit/tree and article byte hashes. Dirty articles and forged/unknown requested commits fail; unversioned and explicit synthetic copies carry null source metadata and no Git-history claim. Ordinary uncommitted code changes can still be built while article bytes match the pinned commit. For an uncommitted article preview use the existing explicit synthetic build mode; it cannot become a release artifact. Source metadata is provenance, not factual approval, a publication date or proof of deployment.

`npm run release:prepare` runs only on a clean checkout after validation. It rechecks source metadata against HEAD, staging/noindex policy and bounded complete asset bytes. It packages the existing `dist`, an independently bundled default-closed Worker, fixed runtime config and canonical `candidate.json`/`candidate.sha256`. It does not rebuild a moving ref or enable identity/D1/GitHub credentials. The Worker embeds the SHA-256 of `release.json`; runtime status reports `releaseCommit` and `releaseManifestVerified` only when the attached asset matches that compiled binding. `releaseVerified` stays false: a manifest match alone is not an independent live-deployment attestation. The controller separately observes the provider version and verifies every public asset's served bytes, noindex headers and runtime binding before recording success.

Artifacts are limited to 256 files/16 MiB total and 4 MiB per file; Worker output is limited to 256 KiB. Inventories reject symlinks, path traversal, extra files, changed config/Worker/assets and wrong source/target pins. The target is fixed to account `c370be29e4065365de03bc8652da2cdc`, Worker `agentic-bible-staging`, origin `https://staging.agenticbible.si`. Config contains ASSETS only, no routes, workers.dev, previews, D1, secret setup, variables or triggers. Provider version preflight rejects any unreviewed binding before activation. Wrangler validation, local serving and uploads use disposable execution copies because Wrangler writes `.wrangler` beside its config; the verified artifact remains unchanged.

## Explicit promotion and rollback

The validation job builds/tests once, then prepares/uploads `release-candidate` with 30-day retention. `.github/workflows/release-staging.yml` has only `workflow_dispatch`, fixed-target concurrency without cancellation, a main-ref check, an owner enablement variable defaulting false, and the `staging` environment. It never runs on a source push or PR automatically. Owner protections must be configured before enablement; merely naming an environment does not create a review policy.

The live entrypoint requires the named repository/main workflow, explicit target confirmation, successful main-push validation run, exact candidate SHA-256, a request UUID and exact active Worker version UUID. It downloads that run's single immutable artifact using read-only GitHub Actions credentials and checks its source against the successful CI head. Deployments recheck current main before upload and activation. PR-only artifacts are review evidence and cannot pass release admission, even if their tests pass.

Cloudflare version upload uses package-pinned Wrangler with machine-readable output, no bundling of replacement source and an exact artifact/request marker. The API adapter observes one 100% active version, verifies the uploaded candidate marker and ASSETS-only bindings, then activates that version through the fixed deployments endpoint without `force`. Mixed traffic, stale current version, foreign versions/bindings and ambiguous responses fail closed. A journal records planned/upload/activation/verification states. Explicit same-UUID retries inspect remote markers and recover lost responses without blind reupload or overwrite. The pinned Wrangler can retry version-create POSTs internally, including after an ambiguous creation, so one upload invocation can create duplicate versions. Recovery validates every exact candidate/request match (full detail marker, UUID and ASSETS-only bindings), then retains a validated CLI/journal/already-active selection or chooses the lexicographically lowest UUID. A missing saved selection, conflicting detail, repeated ID, more than six matches or a full 100-item history fails closed before activation. Completed receipts retain their historical replay behavior. [Fault reproduction and trust boundaries](review/staging-upload-recovery.md).

Two controller upload invocations are allowed per retained journal; pinned Wrangler permits up to three version-create attempts each. Direct adapter API calls are capped at 16 per invocation; Wrangler preflight/asset/session calls are separate from that counter. Uploads remain bounded at 90 seconds, and public verification at 120 seconds plus the current bounded request. These are software/operation bounds, not monetary enforcement or global attempt accounting after losing a workspace. The controller has no automatic retry loop or automatic rollback on an uncertain outcome. Markers are provenance under the exclusive-writer prerequisite, not cryptographic proof of remote bytes; local candidate and complete served-byte/runtime verification remain mandatory.

A completed journal returns its historical receipt without reactivation, including after a later rollback. A receipt records `verifiedAt`; it does not guarantee the version remains current. `hasPreviousVersion` records an observed reference only. Rollback additionally requires a prior successful release-workflow receipt and its exact CI artifact, target/version/source/digest match, and an expected-current pin. It reuses that immutable Worker version and original assets; it does not rebuild current main or revert GitHub content. Provider disappearance, changed secrets, unavailable artifacts or rejected rollback remain explicit failures; no force override, D1 migration, secret reversal or route change is attempted. [Cloudflare documents versions as code/assets/bindings snapshots while external storage state is separate](https://developers.cloudflare.com/workers/versions-and-deployments/).

A missing named Worker produces `release_named_worker_bootstrap_required` before upload; creating it belongs to a separate owner setup. The read-only observation below found the named Worker already exists, so no placeholder or Hello World deployment is required as bootstrap. `none` is valid only for an existing Worker whose deployments API reports no active deployment, rechecked at execution. Its first approved release has no known-good prior release; establish and retain a verified baseline before claiming a rollback target. Actual first upload, hostname attachment and live validation remain unperformed in this handoff.

The deployments API does not provide the controller with a conditional compare-and-swap transaction. Expected-version observations plus workflow concurrency protect this workflow's sequencing; an external deploy can race an in-flight API call. Owner setup must exclude competing Cloudflare Builds/manual deployment writers during an operation. This limitation is not replaced with a new lock service or a claim of global atomicity.
