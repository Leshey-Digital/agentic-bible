# Commit-pinned history and staging releases

This successor preserves PR32 `c8b485f205c55cbbf71cb4770e34de65a9942a18`. GitHub remains canonical source/history. The existing validation workflow is extended with a release artifact; one separately invoked staging workflow consumes it. No second build service, canonical D1 overlay, deployment database or model framework is introduced. No workflow is dispatched and no live resource, credential, route or license is configured by this implementation.

## Source history and artifact

`src/release/source.ts` resolves a full Git commit and verifies all twenty current article files against regular Git blobs at that commit. Public file-history links use that exact SHA, never a moving feature branch. `release-source.json` records the source commit/tree and article byte hashes. Dirty articles and forged/unknown requested commits fail; unversioned and explicit synthetic copies carry null source metadata and no Git-history claim. Ordinary uncommitted code changes can still be built while article bytes match the pinned commit. For an uncommitted article preview use the existing explicit synthetic build mode; it cannot become a release artifact. Source metadata is provenance, not factual approval, a publication date or proof of deployment.

`npm run release:prepare` runs only on a clean checkout after validation. It rechecks source metadata against HEAD, staging/noindex policy and bounded complete asset bytes. It packages the existing `dist`, an independently bundled default-closed Worker, fixed runtime config and canonical `candidate.json`/`candidate.sha256`. It does not rebuild a moving ref or enable identity/D1/GitHub credentials. The Worker embeds the SHA-256 of `release.json`; runtime status reports `releaseCommit` and `releaseManifestVerified` only when the attached asset matches that compiled binding. `releaseVerified` stays false: a manifest match alone is not an independent live-deployment attestation. The controller separately observes the provider version and verifies every public asset's served bytes, noindex headers and runtime binding before recording success.

Artifacts are limited to 256 files/16 MiB total and 4 MiB per file; Worker output is limited to 256 KiB. Inventories reject symlinks, path traversal, extra files, changed config/Worker/assets and wrong source/target pins. The target is fixed to account `c370be29e4065365de03bc8652da2cdc`, Worker `agentic-bible-staging`, origin `https://staging.agenticbible.si`. Config contains ASSETS only, no routes, workers.dev, previews, D1, secret setup, variables or triggers. Provider version preflight rejects any unreviewed binding before activation. Wrangler validation, local serving and uploads use disposable execution copies because Wrangler writes `.wrangler` beside its config; the verified artifact remains unchanged.

## Explicit promotion and rollback

The validation job builds/tests once, then prepares/uploads `release-candidate` with 30-day retention. `.github/workflows/release-staging.yml` has only `workflow_dispatch`, fixed-target concurrency without cancellation, a main-ref check, an owner enablement variable defaulting false, and the `staging` environment. It never runs on a source push or PR automatically. Owner protections must be configured before enablement; merely naming an environment does not create a review policy.

The live entrypoint requires the named repository/main workflow, explicit target confirmation, successful main-push validation run, exact candidate SHA-256, a request UUID and exact active Worker version UUID. It downloads that run's single immutable artifact using read-only GitHub Actions credentials and checks its source against the successful CI head. Deployments recheck current main before upload and activation. PR-only artifacts are review evidence and cannot pass release admission, even if their tests pass.

Cloudflare version upload uses package-pinned Wrangler with machine-readable output, no bundling of replacement source and an exact artifact/request marker. The API adapter observes one 100% active version, verifies the uploaded candidate marker and ASSETS-only bindings, then activates that version through the fixed deployments endpoint without `force`. Mixed traffic, stale current version, foreign versions/bindings and ambiguous responses fail closed. A journal records planned/upload/activation/verification states. Explicit same-UUID retries inspect remote markers and recover lost responses without blind reupload or overwrite. Two upload attempts are allowed per retained journal; API calls are capped at 16 per invocation, uploads at 90 seconds, and public verification at 120 seconds plus the current bounded request. These are software/operation bounds, not monetary enforcement. There is no automatic retry loop or automatic rollback on an uncertain outcome.

A completed journal returns its historical receipt without reactivation, including after a later rollback. A receipt records `verifiedAt`; it does not guarantee the version remains current. `hasPreviousVersion` records an observed reference only. Rollback additionally requires a prior successful release-workflow receipt and its exact CI artifact, target/version/source/digest match, and an expected-current pin. It reuses that immutable Worker version and original assets; it does not rebuild current main or revert GitHub content. Provider disappearance, changed secrets, unavailable artifacts or rejected rollback remain explicit failures; no force override, D1 migration, secret reversal or route change is attempted. [Cloudflare documents versions as code/assets/bindings snapshots while external storage state is separate](https://developers.cloudflare.com/workers/versions-and-deployments/).

The first actual Worker creation is an owner bootstrap handoff, not silently performed here. A missing named Worker produces `release_named_worker_bootstrap_required` before upload. `none` is valid only for an existing Worker whose deployments API reports no active deployment. Initial bootstrap has no known-good prior release; establish and retain a validated baseline before claiming a rollback target. Cloudflare's [versioned deployment walkthrough starts with an initial deployment](https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/). Bootstrap/hostname setup and live validation are unperformed.

The deployments API does not provide the controller with a conditional compare-and-swap transaction. Expected-version observations plus workflow concurrency protect this workflow's sequencing; an external deploy can race an in-flight API call. Owner setup must exclude competing Cloudflare Builds/manual deployment writers during an operation. This limitation is not replaced with a new lock service or a claim of global atomicity.

## Exact setup inputs and owner handoff

| Input | Minimum permission / source | Owner handoff |
|---|---|---|
| Accepted source | Independently reviewed integration into `main`, followed by successful existing validation and candidate artifact | Owner/release maintainer merges only after separate authorization; this task performs none. Current main still has three articles. |
| Protected `staging` environment | Repository administration to set required reviewers, prevent self-review as appropriate and restrict deployment branches to main | Owner configures through GitHub settings. No administration credential is needed by the runtime. |
| Enablement | Repository variable `AGENTIC_BIBLE_STAGING_RELEASE_ENABLED=true`, only after protections/setup | Owner sets it; absent is disabled. |
| Release GitHub reader | Built-in job `GITHUB_TOKEN`: `contents:read`, `actions:read`, same repository | Automatic short-lived job token; no broad PAT or token value in chat. It cannot merge, write content, configure secrets or change settings. |
| Cloudflare release secret | Environment secret `AGENTIC_BIBLE_STAGING_WORKERS_TOKEN`; Workers Scripts Write (dashboard Workers Scripts Edit), scoped to the named Worker where supported, otherwise only the specified account | Owner creates/stores through protected settings after separate authorization, never chat. No Global API key, all-account access, billing, DNS/zone write, D1, KV, R2, AI or account-admin permission is requested. [The deployment endpoint lists accepted write permissions](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/subresources/deployments/methods/create/). Real token/API behavior remains unverified. |
| Named Worker/bootstrap and hostname | Approved initial artifact/version and `staging.agenticbible.si` mapped to the named Worker; route/domain administration belongs to owner | Owner initializes/binds via a separately authorized setup. The release token/workflow does not purchase services or configure DNS/routes. Capture initial version and validate public bytes. |
| Deploy dispatch | `ci_run`, reviewed `candidate.sha256`, UUID `request_id`, exact `expected_active`, action `deploy`, confirmation `agentic-bible-staging` | Release maintainer supplies non-secret pins and obtains environment approval. No moving-ref or latest-artifact selector. |
| Rollback dispatch | Target artifact CI run/digest, prior successful `release-receipt` run, current active UUID, new request UUID, action `rollback` | Maintainer retains both candidate/receipt and confirms Cloudflare version availability. A bare old version ID is insufficient. |
| Recovery | Original candidate/request/expected pins and journal; use a new explicit dispatch for an uncertain outcome, not an uncontrolled retry loop | Operator reviews pending state. Remote markers support recovery when the old job workspace is gone; retained journals provide attempt accounting. CI/artifact-name conflicts on rerunning an old job require deliberate operator handling. |
| Retention and exclusivity | Prior artifacts/receipts/versions kept through the agreed rollback window; one authorized deployment writer | Owner chooses backup/retention and disables competing automatic deploy paths before enablement. Thirty days is the current GitHub artifact setting, not a lifetime guarantee. |

PR32 identity trust, real D1 binding and application GitHub proposal credentials remain separate setup. This artifact deliberately keeps them closed; enabling them needs an independently reviewed binding/configuration contract. Code/content licensing, contribution/privacy terms, provider budgets and live indexing remain unresolved gates for their respective features. This staging release path does not silently enable any of them.
