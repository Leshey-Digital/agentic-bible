# Workers-native GitHub correction proposals

The [runtime gap report](hosted-runtime-gap.md) distinguishes this adapter from live hosted publication. GitHub remains authoritative. A proposal is not a published article; a D1 receipt never changes deployed assets. Frozen PR29 and all twenty Markdown files remain unchanged.

## Deployable boundary and defaults

`wrangler.runtime.staging.jsonc` is a separate candidate for the approved `agentic-bible-staging` target. It binds existing `dist` as `ASSETS` and routes API/admin requests through `src/hosted/worker.ts`; normal reading/search/assets remain assets-first, preserving the static read path. It contains no D1 UUID, route/domain, GitHub credential or production identity setup. Run `npm run runtime:check` for a dry run and `npm run runtime:local` on loopback port 8795. Neither deploys. The existing staging/editorial configs remain unchanged.

The default entrypoint serves static GET/HEAD, forces staging noindex, reports safe capability status and closes admin/write/public-intake routes. Status explicitly has no verified release commit. `LOCAL_EDITORIAL_MODE`, fixture cookies and role headers cannot enable it. The server-created factory exposes three unconfigured ports: verified admin request authorization (including CSRF), immutable approved-note lookup and server-only GitHub transport. The checked-in configuration supplies none. The [integration successor](hosted-corrections-integration.md) implements these ports in the shipped entrypoint behind explicit signed trust, D1 and secret bindings. Merely implementing a function port is not production authentication; the chosen cryptographic verifier/identity and credentials remain separate work. Test ports live only in a test entrypoint and are never imported by the deployable entrypoint.

## One bounded proposal

The HTTP export request contains only an opaque approval UUID, not note text, a role or a GitHub URL. The trusted authority supplies a strictly shaped `verified-admin-github-proposal` note: pinned main Git commit, baseline Markdown SHA-256, existing citation, 20–1,000 characters of reviewed plain text, opaque public reviewer/contribution references and submission revision. Existing `local-synthetic-only`/local-editor approvals are ineligible and are not automatically translated. Approval means an authorized editorial decision, not factual accuracy, source authenticity or licensing rights.

The adapter verifies GitHub main, the pinned base commit/tree and exact article bytes, including a non-truncated bounded base tree with a single normal `100644` blob entry matching the contents response (symlink/executable/submodule paths are rejected), then appends an escaped note while preserving the entire original file and its source-check metadata. It changes only `src/content/articles/tool-use.md`, with at most six note markers. Tree creation always names the pinned `base_tree`; new commit has that exact single parent. It creates a deterministic branch; it never PATCHes, overwrites or force-updates a ref. An existing branch must have the expected whole tree, parent and approval marker, preventing unrelated file changes from entering the proposal. Trusted approval is re-read before branch/PR effects and receipt completion; changed/revoked authority cannot confirm success. Draft PR head/base/marker are checked; main is checked before and after proposal creation. Closed/foreign/changed proposals do not silently reopen or rebase.

This follows the official [Git trees](https://docs.github.com/en/rest/git/trees#create-a-tree), [commits](https://docs.github.com/en/rest/git/commits#create-a-commit), [references](https://docs.github.com/en/rest/git/refs#create-a-reference) and [draft PR](https://docs.github.com/en/rest/pulls/pulls#create-a-pull-request) APIs. Requests are fixed to this repository on `api.github.com`, with manual redirects, omitted browser credentials, JSON/byte bounds and API version 2026-03-10. No network transport is enabled without an explicit server secret binding; the integration successor supplies a restricted native-fetch implementation. Future credential injection must preserve those Request restrictions and never return a token to the browser.

## Reservations and uncertain outcomes

Migration 0008 adds only a proposal outbox, not a production approval/auth table or a remote resource. Actual D1 atomically admits at most four retained rows and claims a 60-second lease. Each network request reserves before dispatch, at most 12 per invocation and 24 lifetime per approval. Responses are capped at 256 KiB; Markdown at 64 KiB; network calls at two seconds with a 25-second orchestration budget. These are software/request bounds, not monetary enforcement or D1/identity-provider latency guarantees. No automatic retries or eviction occur.

Lost ref/PR responses and D1 completion faults remain pending. Explicit retry inspects deterministic GitHub state, verifies it and completes once; historical completed replay returns the receipt without remote reactivation. An expired crashed lease can be reclaimed. Uncertain tree/commit object creation can leave unreferenced Git objects; they do not publish a branch/article and remain bounded by the request budget. This is not a distributed transaction. Revocation racing a remote effect can leave a draft branch/PR requiring deliberate operator closure; it never confirms publication or automatically merges/closes remote work. GitHub changes after a receipt are outside that historical receipt; release must pin and revalidate the reviewed head. A draft proposal always records `published:false` and does not prove an open/current PR or deployed release forever.

## Validation and rollback

`npm run test:hosted` uses real workerd/D1 and a controlled GitHub REST service, including restart, lost responses, D1 completion faults, concurrency, stale/changed/revoked authority, foreign branches, capacity, redirect/response limits and native fetch deadline. All URLs/PR receipts in these proofs are controlled fixtures, not live GitHub creations. A projected note is applied to an isolated candidate source copy and actually built/indexed with twenty entries. `npm run test:hosted:browser` serves that synthetic build through the actual local Wrangler runtime, verifies note reading/search, normal collection/search and closed auth/intake on desktop/mobile. The projection test is not a checkout/build of remote main; main still has three entries.

Run full validation and retained suites sequentially; browser proof requires the controlled projected build from validation. Code rollback returns to PR29; preserve/export any local outbox state deliberately. A future published GitHub correction rolls back by a separately reviewed Git revert/new build and deployment, never by a D1 pointer or receipt mutation. Live rollback/hosting, production identity/gateway and credential provisioning, release-source history references and operational retention remain unconfigured or unimplemented; the integration successor supplies the verifier/approval/transport code. No main/PR merge, live deployment, credential configuration, paid call, indexing or license change is included.
