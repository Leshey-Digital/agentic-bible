# Hosted integration settings boundary

## Problem and outcome

The reviewed secure integration contract is callable but unmounted. Add the smallest exact hosted API boundary and a typed trusted server-code adapter seam, retaining direct cryptographic verification and every existing contract guard. Prove default closure and synthetic delegated behavior in actual local workerd. [Boundary contract](../../../docs/hosted-integration-settings-boundary.md).

## Scope and non-goals

Add only `/api/admin/settings/integrations/github-content`, GET/POST, exact origin/path/no-query checks, fixed safe responses and optional `Ports.integrationSettings`. Preserve `RuntimeEnv`, `configuredPorts`, local measurement settings and the reviewed contract/identity code. Test-only server code supplies disposable memory adapters and generated signing trust.

No UI, persistent vault, schema/dependency/configuration change, live binding/provider call, OAuth, account/security setup, credential, release/deployment, main update, publication or PR. No caller boolean/role or fixture session grants hosted authority. No claim that native fake tests establish persistent storage or live readiness.

## Options, dependencies and risks

Leaving the contract unmounted retains no hosted boundary. Building persistent storage or inferring adapters from existing env/token would exceed scope and weaken the closed default. The selected explicit trusted-code seam permits native route verification while shipped configuration remains closed.

Costs are local test execution only, with no outbound requests or cloud resources. Risks are accidental env activation, path aliases, reuse of unsigned verifier ports and overclaiming a vault; direct delegation, default-entrypoint workerd tests and explicit docs cover those boundaries. Future production adapters still need durable atomic storage, logging exclusion, scoped transport, revision serialization and setup approval. No new provider decision is made.
