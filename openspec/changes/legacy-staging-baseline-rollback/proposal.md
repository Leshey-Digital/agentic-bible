# Add guarded rollback to a pre-controller staging baseline

The existing active staging version predates the release controller and has no candidate marker or `verified-serving` receipt. The first qualified deployment does not need an earlier receipt, but the current rollback CLI cannot target this legitimate legacy version. Add an explicit, independently pinned legacy-baseline record and a separate rollback action. Preserve the qualified-candidate receipt format and all existing owner, independent-review, exclusive-writer, expected-active, exact-binding, journaling, and served-byte checks.

The baseline record describes provider-observed version identity (ID, number, creation metadata, source, script ETag, marker absence and exact bindings), the original 100% deployment, read-only runtime invariants, and hashes/sizes for served public assets. It is not a candidate, qualification, or `verified-serving` receipt. Rollback re-fetches and compares provider metadata immediately before the guarded deployment request, then verifies the restored asset bytes and closed runtime behavior. No upload, baseline activation, credential access, or production change is included.
