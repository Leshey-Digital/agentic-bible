# Truthful reader metadata and revision context

Give readers an accurate way to distinguish source-check dates, actual source-file changes, publication receipts, and human editorial certification. The twenty-entry collection has been read across external and internal review, while factual claim verification was sampled; no blanket fact-check or universal human certification should be implied.

Derive article change records from the actual Git history of each Markdown file at the build's pinned source commit. If the repository or history is unavailable, say so rather than substituting a source-check, build, or deployment date. Keep local maintenance receipts and correction/restoration records visibly separate from source lineage. Add practical link/citation copying with visible manual-copy text when JavaScript or clipboard access is unavailable.

Use the existing canonical discovery policy for page previews. History should be a public canonical destination in explicit production builds and remain noindex without a canonical in staging or synthetic builds. Make metadata specific to each page, including page title, description, Open Graph, and Twitter fields, without inventing authorship, images, publication dates, or modification dates.

Clarify the actual review process and limits in About, including that future review cadence is undecided. Keep the current cream/green serif identity, original article text, static delivery, current stack, and all release boundaries. No new framework, tracking, paid call, deployment, or expanded persistent access is in scope.
