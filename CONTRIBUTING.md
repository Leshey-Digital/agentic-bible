# Contribution workflow

**Public contributions are on hold pending published licensing and submission terms.** Do not send third-party code, article text, or source datasets yet. The following is a proposed workflow for authorized maintainers and future contributors.

1. Define the reader problem or correction in an issue, including source URLs and acceptance criteria. Never post credentials, private data, or vulnerability details.
2. For a material change, use the [change template](docs/workflow.md). Keep article corrections small and cite evidence at the affected claim.
3. Work on a focused branch and open a draft PR using the repository template. Disclose generated text/code and its human verification.
4. Review provenance, factual accuracy, accessibility, security, link integrity, cost, and rollback. A model's confidence is not evidence.
5. Run the checks documented in README: documentation links, types, static build, generated links, browser flows and local staging dry run. Report results separately from editorial approval.
6. The maintainer accepts or requests changes. Merging and deploying are distinct actions; neither is automatic.

Future on-site proposals must pass technical, evidence and abuse validation, preserving attribution and history. The founder approved automatic article publication with post-publication human admin review flags on 2026-10-16; do not turn moderation into universal human editorial preapproval. Abuse controls and safe handling of untrusted URLs must be implemented before enabling the form. GitHub will remain a contribution route after terms are resolved.
